Run the maintainer commands in this page from a clone of the [library repository](https://github.com/groundsgg/library-motd). Use published packages for ordinary integrations.

The canonical package is [`@groundsgg/motd` on npm](https://www.npmjs.com/package/@groundsgg/motd). GitHub Packages mirrors exactly the same archive and version. npm consumers do not need GitHub credentials.

## Normal releases

1. Merge Conventional Commit PRs into `main`. The Release workflow runs all CI checks before updating the Release Please PR.
2. Review and merge the release PR after its CI checks pass. Release Please updates `package.json`, the lockfile, the changelog and its manifest, then creates `vX.Y.Z` and a GitHub release.
3. The same workflow publishes its tested archive to npm through OIDC and to GitHub Packages with `GITHUB_TOKEN`. There is no long-lived npm token.

Release Please uses the organization secret `RELEASE_PLEASE_TOKEN`, belonging to `grounds-bot`, to create release PRs, tags and GitHub releases. The secret must remain available to this repository with permission to write contents, pull requests and issues. Bot-created PRs trigger CI automatically. If GitHub requests approval for the bot's pull-request workflow, review and approve that run from the PR before merging.

Both registries receive the same bytes. The publisher rejects tag/version mismatches, unknown registries and existing versions with different integrity. Authentication and network errors fail the job. To recover a failed publication, run the Release workflow manually with the existing release tag. It rebuilds and verifies the tagged source; an already published version is skipped only when its SHA512 integrity matches. Changes to package tooling must be released under a new version.

The `npm` and `github-packages` GitHub environments isolate publication permissions. npm's trusted publisher must name `groundsgg/library-motd`, workflow `release.yml` and environment `npm`. Actions run on GitHub-hosted Ubuntu runners. Node 24 supplies an npm version supporting trusted publishing.

## Current and superseded validations

The workflow binds release work to the exact commit verified by CI. Before
running Release Please, it queries the current `main` SHA and checks both
revision values. If another PR merged during validation, the older successful
run emits a superseded notice and skips Release Please and both publication
jobs. The newer queued run validates the updated head. A superseded result is
an expected outcome when merging several feature PRs in sequence.

API failures, empty or malformed revisions and output-write failures still fail
the guard. A current verified run may update the release PR without publishing
anything. Normal publication additionally requires a newly created release,
the current-verification flag and the existing post-action assertion that the
release SHA matches the verified artifact's SHA. Registry, version and integrity
checks remain in place.

`main` can still move between the precheck and the Release Please API call.
The post-action SHA assertion blocks mismatched package publication, but it
cannot undo GitHub release or PR side effects already made by Release Please.

Explicit recovery with a stable existing release tag follows its separate
validation path. It verifies the tagged source and requires an existing
non-draft GitHub release; it does not require that tag to equal today's `main`.

The historical [superseded-run failure](https://github.com/groundsgg/library-motd/actions/runs/40593996490)
used the older fail-on-mismatch workflow and remains recorded. All its validation
jobs passed before the stale-revision guard failed. The correction in
[#127](https://github.com/groundsgg/library-motd/issues/127) applies to later
workflows; rerunning that old workflow against a newer `main` does not adopt the
fix. Tests execute the actual Bash guard and evaluate downstream conditions with
GitHub's expression library using controlled API responses. They perform no
release or registry writes.

## First npm publication

npm requires an existing package before configuring a trusted publisher. An npm organization owner must publish the first validated CI archive once using their normal npm login and complete npm's interactive authentication, then configure:

```sh
npm trust github @groundsgg/motd \
  --repository groundsgg/library-motd \
  --file release.yml \
  --environment npm \
  --allow-publish --yes
```

This needs npm 11.15 or newer and an owner account with two-factor authentication. Configure the trusted publisher just before the next automated publication; npm expires a new publisher configuration if unused for two days. Verify an actual OIDC publication within that period; checking an already published version does not validate the new connection. Subsequent releases use OIDC. Restrict token publishing in the npm package settings after verifying the first automated release.

GitHub Packages uses the repository's `GITHUB_TOKEN`. Verify package visibility after its initial publication; package visibility is managed separately from repository visibility.

## Installing the GitHub mirror

GitHub's npm registry requires authentication even for public packages. Configure the consumer's `.npmrc`:

```ini
@groundsgg:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}
```

Use a token with `read:packages`, or an appropriately authorized Actions `GITHUB_TOKEN`. For ordinary consumers prefer npmjs.com; this repository's `.npmrc` explicitly selects it for `@groundsgg`.
