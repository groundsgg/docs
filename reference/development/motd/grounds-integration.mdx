---
title: "Integrate with Grounds"
description: "Connect the public library to application persistence and multi-proxy runtime data without coupling its core to Grounds."
---

Consume `@groundsgg/motd` through its public package. Grounds is one host of the
same standalone library, not a required service or a separate editor model.

## Separate the three boundaries

| Boundary                  | Responsibility                                                                                                                    |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Portal/application        | Present controls, enforce permissions, manage drafts, save with conflict protection, and supply viewer context.                   |
| Configuration/API adapter | Validate saved documents, compile a runtime template, validate image data, and retain application-specific envelope semantics.    |
| Proxy/runtime             | Evaluate the compiled template with an authorized network snapshot and retain a usable previous configuration when refresh fails. |

Use compatible published package versions and committed lockfiles. Do not vendor
an unversioned local library build into a consumer. Keep older runtime fallback
formats only as an explicit adapter compatibility boundary.

## Persist intent, not a preview

Store `ServerListDocument` through the consuming API. Client version, row/menu
presentation, region, example count, ping, and toolbar placement are UI context.
Changing them must not save live values into the document or increment its
server configuration version.

The Portal's example-player setting is a presentation value, not a claim of
live network presence. Only replace labeled examples after wiring an authorized
data source for the selected environment.

## Preserve historical aligned source

Forge checks that the editor document, its MiniMessage fallback and the compiled
runtime template agree. A library upgrade can change the generated padding
without changing the document's text or alignment intent. Existing saved
normal and maintenance documents must remain readable and saveable through
that transition.

The API adapter first compares the supplied fallback with the active library's
output. For aligned MOTDs only, it can also accept the exact output of the
pinned `@groundsgg/motd@0.1.1` compatibility serializer. Both the top-level
`text`/`motd` and `editor.fallbackText` must match. The runtime template must
still exactly match the current compiler's output.

This compatibility path validates the historical MOTD model and rejects unknown
node or style semantics, including native sprite nodes and newer shadow fields.
It does not approximate whitespace or remove leading spaces to make a mismatch
pass. Version, icon, player and hover settings stay under the current contract
and remain unchanged.

Reads preserve the stored fallback bytes and configuration version. You can
load and save an unchanged historical document; a new edit can use the active
serializer's canonical output. A legacy fallback-only edit still discards stale
editor metadata instead of restoring the old text. An actually contradictory
source or runtime template is rejected.

<Info>
This adapter prepares the dependency upgrade. Forge's active library dependency
remains at `0.1.1` until a compatible version is published and explicitly pinned.
Do not enable the [native sprite picker](/reference/development/motd/sprites)
in Portal before that API upgrade. An adapter merge alone does not publish an
npm version or activate a Portal or proxy deployment.
</Info>

## Choose the display size

In **Preview settings → Preview size**, **Automatic (whole GUI scales)** chooses
the largest whole GUI scale that fits the content width of its own editor canvas
or viewer container. It scales both axes equally and leaves the remaining space
free. For a 309-GUI-pixel scene, 632 or 900 CSS pixels of available width both
select 2× (618 CSS pixels); 927 CSS pixels selects 3×.

The minimum automatic scale is 1×. Below that scene width, the Portal retains
the native row width and allows horizontal scrolling, preserving the MOTD's
line breaks. The editor row starts at the canvas padding instead of centering
an odd remaining gap, which could add a half-pixel offset. The toolbar keeps
its normal size. Each viewer measures its own container, so the editor and
sidebar preview can use different automatic scales.

This avoids fractional GUI transforms that soften text and thin ping bars.
It is not a claim of pixel-perfect output at every browser zoom level or device
pixel ratio.

Choose **Fixed client size** to select a GUI scale from **1×** through **4×**.
The row retains the selected client geometry and scale when its container
shrinks. Narrow editor canvases and previews scroll horizontally instead of
clipping or compressing the row. The editor and its associated preview share
this choice.

`NetworkPreviewSettings.sizeMode` is optional and defaults to `"fit"`.
`guiScale` is an optional `1 | 2 | 3 | 4`, defaulting to `2` in fixed mode.
Both are local presentation settings; changing them does not dirty or save the
MOTD. They map to the published library's existing `context.guiScale` and
`context.viewportWidth`, with no Portal-specific package API.

See [embedding](/reference/development/motd/embedding) for the standalone sizing
contract. This Portal change does not require a new npm release.

## Use network-wide data

For a global count, supply authoritative presence across all proxies. For a
regional view, define region membership and unknown-region handling explicitly.
Keep environment boundaries, deduplication, freshness, and failure semantics in
the provider; the library does not infer them or perform network polling.

Test at least two proxies and a remote player. Include unavailable/stale data,
permission denial, region changes, and isolated Stage/Production settings. Do
not silently use local proxy counts when the global source is unavailable.

### Read the authoritative presence API

`service-player` exposes `GET /v1/players/counts/proxies` with this response
shape:

```json Example session snapshot
{
  "proxies": [
    { "proxyId": "proxy-eu-1", "region": "eu", "players": 12 },
    { "proxyId": "proxy-us-1", "region": "us", "players": 8 }
  ],
  "total": 20
}
```

Use `total` for the service's network-wide count. Sum rows for an explicitly
selected region when you need a regional view. A missing region is unknown;
do not assign it to the selected region. Historical sessions without a proxy
identifier can contribute to `total` without appearing in `proxies`, so do not
replace `total` with the row sum. Keep any unassigned remainder separate from
known regional counts.

`GET /v1/players/counts/servers` groups the same session store by backend server.
Its `total` also includes players who have not reached a backend yet. Adding
backend counts is therefore not a substitute for the network total.

Both endpoints require a workload bearer token when service authentication is
enabled. The current verifier checks the cluster's signing keys and the
`grounds-services` audience; the response does not identify Stage or Production.
Bind the provider's URL and credential to the selected environment in the host.
Keep workload credentials on the backend, behind the Portal's existing network
read permission checks. A configuration-service credential is not implicitly a
presence-service credential.

### Distinguish observation time from session freshness

These endpoints count stored sessions. Their queries do not exclude old
heartbeats directly; the scheduled cleanup removes expired sessions. The
defaults are a 90-second session TTL and a 30-second cleanup interval. Cleanup
delays or failures can extend that period, so these settings are not a hard
freshness guarantee.

The response contains no observation timestamp, heartbeat watermark or maximum
capacity. A host's fetch-completion time records receipt, not the last time every
player was confirmed online. If you retain a previous response after a failed
refresh, label it as stale; a `401`, `503` or disconnected provider must not
become a fresh count of zero. Keep advertised maximum capacity under its own
configuration instead of deriving it from online presence.

### Configure the Forge provider

Forge exposes `GET /v1/admin/network/{stage|prod}/presence`. It requires
`ADMIN_AREA_ACCESS` and the selected environment's view or manage permission,
independently of configuration-service availability. Configure these optional
backend bindings to connect the corresponding presence service:

| Environment | HTTP(S) origin | Projected workload token file |
| --- | --- | --- |
| Stage | `NETWORK_PRESENCE_STAGE_URL` | `NETWORK_PRESENCE_STAGE_TOKEN_FILE` |
| Production | `NETWORK_PRESENCE_PRODUCTION_URL` | `NETWORK_PRESENCE_PRODUCTION_TOKEN_FILE` |

Use a service origin without a path, credentials, query or fragment. Forge
requests the fixed `/v1/players/counts/proxies` route and rereads the token file
on each request. Neither environment inherits the other's connection or the
configuration client's credential. Bind each origin to the intended environment;
the upstream API cannot attest that mapping for you.

The response includes `environment`, `source: "service-player"`, `receivedAt`,
`total`, aggregated `regions: [{ region, players }]`, and `unknownRegion`.
`unknownRegion` includes null-region rows and any remainder not attributable
through the upstream proxy groups. Forge does not forward proxy identities or
workload credentials. `receivedAt` records receipt and validation, not heartbeat
freshness or an advertised maximum capacity.

A disconnected provider or upstream failure returns `503`; invalid count data
returns `502`. Responses use `Cache-Control: private, no-store`. Forge follows
no redirects, bounds the complete request to five seconds and limits streamed
JSON to 256 KiB. It does not cache a previous count or return zero on failure.
Both connections remain unavailable until their bindings are supplied.

### Choose a Portal preview source

In **Preview settings → Player count source**, choose:

- **Example values** to keep the existing manually chosen example count. This
  default does not request presence data.
- **Network sessions** to use the selected environment's authoritative `total`.
- **Selected region sessions** to use only the known count for **Preview region**.
  Regions reported by the provider also appear in that selector. Missing regions
  contribute zero known sessions; unassigned sessions remain separate.

Editor and viewer share the same snapshot. The library evaluates player-count
rules and `{{players}}` from that context, including offset and headroom rules.
The source supplies online counts only: configured maximum rules remain
independent, and an inherited maximum still uses the labeled 500-player example.
Changing the source, region or received snapshot does not dirty or save a MOTD.

Portal refreshes an enabled source every ten seconds while the page is active.
Its receipt-age display measures the browser's last successful response, not
the upstream heartbeat age. A response becomes **Stale snapshot** at 30 seconds
or immediately after a failed refresh. Previously received counts can remain
visible under that label. Without a successful snapshot, Portal explicitly
labels its example fallback; an authorization denial discards the displayed
cached counts and uses that labeled fallback too. Stage and Production use
separate queries, and a late response from a previous environment cannot replace
the selected environment's snapshot.

<Info>
This integration uses the published library without adding a transport to its
core. Source tests and local HTTP/browser fixtures do not establish production
connectivity or activate deployment bindings. Package release, Portal activation
and proxy rollout remain separate actions.
</Info>

## Maintenance inheritance

Your adapter must distinguish an inherited field from an explicit reset. For
example, choosing automatic version mode, removing an icon, or unhiding players
can be deliberate overrides even though they resemble defaults.

Keep this application intent in an adapter envelope or JSON-only extensions,
not a new mandatory Grounds field in the npm core. If you enrich editor changes
with `mapChange`, keep metadata in the same history transaction so Undo followed
by Save restores the intended inheritance.

### Start from the normal MOTD

In the selected environment's Maintenance tab, **Copy normal MOTD** replaces
only the maintenance MOTD draft with a snapshot of the **saved** normal MOTD.
It retains formatting and semantic line alignment while preserving other
maintenance status overrides, the maintenance window and player messages.
Edit that draft independently, then choose **Save maintenance** to apply it.
Copying does not save, enable maintenance, change the normal MOTD or create an
ongoing synchronization link. Later normal-MOTD refreshes do not overwrite the
copied draft. Read-only users cannot copy or save.

**Use normal MOTD text** has different semantics: an empty maintenance MOTD
continues to inherit the normal text. Turning inheritance off starts an
independent copy with its alignment metadata intact. Unsaved edits in the
Server message tab are not the saved normal snapshot; save those first if you
want to use them as the maintenance starting point.

Avoid copying the generated MiniMessage fallback manually when the source
contains dynamic placeholders and alignment. Fixed leading spaces computed
for the literal `{{region}}` will no longer center the line after the proxy
resolves it to a shorter value such as `eu`. Preserve the document's alignment
intent so the runtime measures the resolved text before adding spaces.

## Validate the actual consumer

Test the installed package and the production bundle, not only source aliases.
Exercise viewer/editor context synchronization, read-only inspection, maintenance
inheritance, save conflicts, and narrow layouts through the real application
route with isolated fixtures. Keep test authorization separate from production
data and preserve existing activation flags during unrelated rollouts.

For runtime verification, record whether a test uses real proxy processes,
production handlers with local adapters, or live service delivery. Those are
different evidence levels; a local harness does not certify a live broker or
production deployment.
